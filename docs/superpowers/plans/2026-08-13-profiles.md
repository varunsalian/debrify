# Multi-Profile Architecture and Implementation Plan

> **Status:** Revised after independent repository review. Safe to begin Task 1 validation/spikes; implementation beyond the gated platform foundations and production migration remain disabled until their acceptance and rollout gates pass.

> **Companion audit:** Execute the [Multi-Profile Implementation Review Plan](./2026-08-13-profiles-review.md) before enabling profile activation or migration.

**Goal:** Add Netflix-style local user profiles to Debrify. Each profile has independent settings and activity, may have an optional PIN, and receives explicit access to shared integrations. Existing installations migrate into one active, unpinned Admin profile without changing current startup behavior.

**Supported platforms:** Android, Android TV, iOS, tvOS, macOS, Windows, and Linux. Web is explicitly out of scope.

**Architecture:** Introduce an early device-level profile bootstrap, an explicit immutable `ProfileScope`, profile-scoped preference/database/directory generations, device-owned connection resources with grants, and owner-tagged long-running jobs. Preserve `StorageService` as the compatibility facade while moving its implementation behind scoped stores. Profile switching and restore publication are controlled lifecycle transitions, not navigation or category-by-category mutation. On tvOS, purgeable SQLite/files are projections of a compact platform recovery store rather than the sole authority.

**Migration promise:** After updating, a current user sees the same app and data they had before. Their data belongs to an automatically created Admin profile. With only that profile present, Debrify does not show a picker or require a PIN.

## Product and engineering decisions

Treat these as the first-release defaults. Changing one requires an explicit plan amendment because several storage, authorization, and migration guarantees depend on them.

1. **Roles:** `admin`, `member`, and `child`. At least one enabled Admin must always exist.
2. **Profile count:** No hard product limit initially; UI should remain comfortable up to eight profiles.
3. **PIN meaning:** A local application access gate, not a claim of OS-level encryption or protection from a device owner with filesystem access.
4. **PIN defaults:** Optional; lock on cold launch/profile switch. Lock-on-resume and inactivity timeout are per-profile options.
5. **Credential sharing:** Connections are granted by reference. Secrets are never copied into member preferences and are hidden unless the grant permits `revealSecret`.
6. **Shared-account warning:** Sharing Trakt/Simkl or a mutable cloud account must warn that remote history, scrobbles, added torrents, and deletions affect the same upstream account.
7. **Background work:** Downloads and recordings continue after switching profiles, remain owned by the creator, and are hidden from other non-Admin profiles.
8. **Profile deletion:** Existing files on public/user-selected storage are retained by default. Profile metadata, schedules, private databases, and grants are removed after an explicit job-handling confirmation.
9. **tvOS Top Shelf:** Personalized Top Shelf content is hidden while its owning profile is locked. Multi-profile installations default to no personalized Top Shelf until an Admin opts in.
10. **Single-profile startup:** Auto-enter the sole unpinned profile. Show the picker when multiple profiles exist or when the sole profile requires a PIN.
11. **Role/policy precedence:** A role defines the maximum authority a profile can receive; feature policy and resource grants can only narrow that authority. Only an enabled Admin can manage profiles, even if malformed imported policy JSON says otherwise.
12. **Fresh-install onboarding:** Create the first Admin before application onboarding. Device onboarding runs once per installation; the profile wizard owns setup for every later profile.
13. **Credential source of truth:** A migrated credential is writable only through its connection resource. It is never copied into profile preferences or synchronized back to legacy keys.
14. **Background authorization:** PIN state is a UI access boundary and does not pause already-authorized background work. Resource revocation and policy changes follow the job capability rules in Task 9.
15. **Active-profile authority:** On Android, iOS, macOS, Windows, and Linux, `profiles.db` is the source of truth for active profile, bootstrap, migration, activation recovery, and visible data generation. Native/device preferences are revisioned mirrors only. tvOS uses the durability exception below.
16. **One-way activation:** The rollout flag may prevent new installations from migrating, but a committed installation always stays on profile storage. No remote kill switch may send it back to stale legacy data.
17. **Admin re-authentication:** Sensitive Admin actions require that Admin's PIN when configured; otherwise use platform owner authentication when available or a deliberate local confirmation. Do not force the migrated unpinned Admin to create a PIN.
18. **tvOS durability:** `Library/Caches` and `tmp` are purgeable and never authoritative. A compact, sharded, versioned `TvOsProfileRecoveryStore` in runner-only, device-only Keychain items is authoritative for registry/security/configuration recovery; UserDefaults is only a revisioned performance mirror, while `profiles.db` and activity/catalog files are rebuildable projections. Profile rollout on tvOS is blocked if physical-device size/performance/eviction tests cannot prove this design.
19. **Restore visibility:** “Atomic restore” means an atomic visibility/generation swap after complete shadow staging. It does not mean a transaction spanning SharedPreferences, unrelated SQLite files, native stores, and the filesystem.
20. **Desktop process model:** The first profile release is single-instance on macOS, Windows, and Linux. Secondary launches forward URLs/files/arguments to the primary process and exit.
21. **Automatic OS backup:** Device-bound profile state is excluded from Android/Apple automatic backup and device transfer. Encrypted v3 export/restore is the supported portability mechanism.

## Non-goals for the first release

- Cross-device synchronization of profile activity.
- Separate OS accounts, processes, sandboxes, or filesystem permissions per profile.
- Encrypting every profile database with the profile PIN.
- Simultaneous active Flutter profiles or multiple profile windows.
- Supporting concurrent Debrify desktop processes against the same profile store.
- Web support.
- Turning dormant Reddit/Lemmy search code back on.
- Sharing arbitrary live mutable preferences between profiles. Settings may be copied as a creation template, then diverge.

## Data ownership contract

Every persistent value must have exactly one scope.

| Scope | Examples | Rule |
|---|---|---|
| Device | Profile registry, active profile ID, migration state, updater policy, remote device identity, filesystem grants, hardware safety settings | Never automatically copied into a profile |
| Profile | Appearance, Home rows, filters, Quick Play/player/subtitle choices, selected addons/destinations, history, resume, favorites, playlists, watchlists, source bindings | Never read through another active profile |
| Connection resource | Debrid accounts, PikPak, WebDAV, Trakt, Simkl, MDBList, IPTV providers, Stremio manifests, Jackett/Prowlarr | Owned once and granted by reference |
| Owner-tagged job | Downloads, active recordings, recording schedules, durable retries, notifications | Device-executed with immutable `ownerProfileId` |
| Shared public cache | IMDb/TVMaze metadata and non-personal artwork | May be global only when the cache key contains no private endpoint/account input |
| Profile/resource cache | Provider account info, Stremio catalog results, tracker libraries, credential-bearing IPTV/EPG data | Key by profile and/or resource ID |
| Ephemeral session | Active player state, temporary dialogs, in-flight UI state | Capture the originating profile session; never persist into the next active profile |

Default rule: unknown Debrify-owned state is profile-scoped. Device scope requires an explicit allowlist entry and a reason.

Durable job queues, downloader-plugin records, native recording stores, schedule payloads, completed-download history, and recording ownership indexes are never placed under the active profile's preference namespace or directory. They use a device-level `DeviceJobStore` contract and immutable owner metadata. Profile services may only query filtered views of those stores.

### Device-level settings proposed for the allowlist

- Revisioned native mirrors of profile schema, migration state, visible generation, and active profile. `profiles.db` is authoritative off tvOS; the published Keychain recovery manifest is authoritative on tvOS.
- Device-level `app_onboarding_complete`; each profile separately owns `profile_setup_complete`.
- Remote static keypair, remembered peers, and known receiver pins.
- Catalog of authorized download/recording destinations and persisted OS/SAF grants. A profile may own a preferred destination reference; each job snapshots the resolved destination.
- Recording engine availability and device-wide concurrency capacity.
- Hardware/render fallback state and other capability-derived safety settings.
- App update policy and ignored update version.
- Support remote-config cache and device-wide campaign dismissal.
- Installed custom font asset catalog; the selected font remains profile-owned.
- Analytics SDK/device session state. Never attach profile names or stable profile IDs to analytics.

All other existing app preferences begin as profile-owned unless Task 1 proves otherwise.

### Platform durability and availability matrix

| Platform | Registry/configuration authority | Rebuildable/private data | Backup/export path | Downloads/recordings |
|---|---|---|---|---|
| Android / Android TV | `profiles.db`, platform key provider, scoped generations | Caches; regenerable projections | v3 file export/import and reliable remote package transfer | Existing supported native/plugin downloads; Android DVR where currently supported |
| iOS | `profiles.db`, Keychain, scoped generations | Caches | v3 document export/import and reliable remote package transfer | Existing plugin support only; no Android DVR |
| macOS | `profiles.db`, Keychain, scoped generations | Caches | v3 file export/import and reliable remote package transfer | Existing desktop download/DVR behavior while app support permits |
| Windows | `profiles.db`, DPAPI, scoped generations | Caches | v3 file export/import and reliable remote package transfer | Existing desktop download/DVR behavior while app is running |
| Linux | `profiles.db`, Secret Service or explicit fallback, scoped generations | Caches | v3 file export/import and reliable remote package transfer | Existing desktop download/DVR behavior while app is running |
| tvOS | Sharded runner-only `ThisDeviceOnly` Keychain recovery generations; UserDefaults/`profiles.db` are mirrors/projections | All writable SQLite/files under `Library/Caches`, including activity/catalog data | Reliable authenticated remote package transfer; no cache file may be presented as a durable backup | Unsupported in v1 unless a tvOS-native implementation is added and validated |

`TvOsProfileRecoveryStore` contains only bounded recovery-critical state: schema/recovery generation, profile identity/role/policy/lock metadata, active profile, onboarding/migration state, bounded must-survive profile preferences, resource public metadata, grants/bindings, and per-resource secrets. Store a small manifest/published-generation item plus sharded profile/resource items so no unbounded Keychain value is created. Use a runner-only access group and device-only accessibility; the Top Shelf extension receives no recovery or resource entitlement. Large activity/history/catalog databases, artwork, EPG, and Top Shelf media remain caches and may be lost after eviction; the UI must say so and offer encrypted remote backup before destructive operations.

Every tvOS recovery mutation uses immutable Keychain items plus checksums/MACs and an atomically updated published-manifest item. Write/read-verify every new shard first, update the published manifest last, then refresh UserDefaults/SQLite projections. Bootstrap selects only the complete published manifest, repairs missing/stale projections, prunes abandoned shards, and never replaces a recoverable registry with an empty profile. Keychain loss, size/latency failure, or an invalid recovery manifest enters explicit recovery/remote-restore UI. Do not add iCloud synchronization implicitly; if the Keychain feasibility gate fails, pause tvOS profile rollout pending an explicit cloud-backed design.

Bind the tvOS recovery manifest to an `installInstanceId` kept in standard UserDefaults and inside the signed Keychain manifest. Ordinary cache eviction leaves that marker intact. A missing marker is a fresh install and must not silently resurrect Keychain items that may have survived uninstall; clear/quarantine them only after recovery UI policy runs. A restored/mismatched marker without its device-only Keychain authority never activates copied profile state and instead offers authenticated remote restore.

Automatic OS backup/device transfer excludes file-backed profile registries/generations/databases, resource ciphertext, device keys, job stores, native schedules, and other device-bound state. Apple preference mirrors that cannot be excluded per key carry a device-key-bound generation/MAC and are ignored if restored without the matching device-only authority; they can never trigger fresh or partial profile activation. User-selected public media remains governed by its OS/location. The v3 backup manifest is the only supported cross-device graph restore.

### Bootstrap and onboarding state machine

Bootstrap must distinguish these cases before any profile-owned service opens:

| Installation state | Required result |
|---|---|
| Profiles feature disabled in an intermediate build | Enter `LegacyCompatibilityScope`, which maps to current unprefixed preferences and root paths without moving or duplicating data |
| Fresh install with profiles enabled | Transactionally create one unpinned Admin, activate it, then run device/application onboarding |
| Existing install with profiles enabled | Run the journaled legacy migration, activate `legacy-admin-v1`, and preserve the existing onboarding completion state |
| Existing committed profile installation | Reconcile any interrupted activation, select the authoritative active profile, then enter `ProfileGate` |
| Corrupt registry or unrecoverable migration | Do not initialize profile services; offer privacy-safe diagnostics, retry, and non-destructive recovery/export rather than silently creating an empty profile |

`app_onboarding_complete` is device-owned. `profile_setup_complete` is profile-owned. Completing the Admin creation wizard marks a later profile set up and must not send it through the legacy whole-app onboarding flow. A fresh first Admin completes `profile_setup_complete` as part of initial onboarding. Skipping onboarding and importing configuration must set both markers deliberately, never incidentally.

## Core domain model

Use `UserProfile` rather than `Profile` to avoid collision with existing Quick Play and theme “profile” terminology.

### Device profile database

Create `profiles.db` with foreign keys enabled on every connection. IDs are generated opaque identifiers and are the only values permitted in scoped paths; names never participate in a path or preference key. Use schema migrations rather than destructive recreation. The following is the minimum logical schema; exact SQLite syntax may be adjusted while preserving the constraints:

```sql
PRAGMA foreign_keys = ON;

CREATE TABLE user_profiles (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  avatar_key TEXT,
  role TEXT NOT NULL CHECK(role IN ('admin', 'member', 'child')),
  policy_json TEXT NOT NULL,
  policy_schema_version INTEGER NOT NULL,
  authorization_revision INTEGER NOT NULL DEFAULT 1,
  lifecycle_state TEXT NOT NULL DEFAULT 'active'
    CHECK(lifecycle_state IN ('staging', 'active')),
  visible_data_generation INTEGER NOT NULL DEFAULT 1,
  profile_setup_complete INTEGER NOT NULL DEFAULT 0,
  pin_reset_required INTEGER NOT NULL DEFAULT 0,
  pin_hash BLOB,
  pin_salt BLOB,
  pin_params_json TEXT,
  failed_pin_attempts INTEGER NOT NULL DEFAULT 0,
  locked_until_ms INTEGER,
  lock_on_resume INTEGER NOT NULL DEFAULT 0,
  inactivity_timeout_minutes INTEGER,
  created_at_ms INTEGER NOT NULL,
  updated_at_ms INTEGER NOT NULL,
  disabled_at_ms INTEGER
);

CREATE TABLE device_state (
  singleton_id INTEGER PRIMARY KEY CHECK(singleton_id = 1),
  schema_version INTEGER NOT NULL,
  bootstrap_state TEXT NOT NULL,
  migration_state TEXT NOT NULL,
  active_profile_id TEXT,
  registry_generation INTEGER NOT NULL DEFAULT 1,
  activation_revision INTEGER NOT NULL DEFAULT 0,
  activation_state_json TEXT,
  updated_at_ms INTEGER NOT NULL,
  FOREIGN KEY(active_profile_id) REFERENCES user_profiles(id)
    ON DELETE RESTRICT DEFERRABLE INITIALLY DEFERRED
);

CREATE TABLE connection_resources (
  id TEXT PRIMARY KEY,
  type TEXT NOT NULL,
  label TEXT NOT NULL,
  owner_profile_id TEXT NOT NULL,
  public_config_json TEXT NOT NULL,
  sealed_secret_payload TEXT,
  secret_payload_version INTEGER,
  authorization_revision INTEGER NOT NULL DEFAULT 1,
  created_at_ms INTEGER NOT NULL,
  updated_at_ms INTEGER NOT NULL,
  disabled_at_ms INTEGER,
  FOREIGN KEY(owner_profile_id) REFERENCES user_profiles(id) ON DELETE RESTRICT
);

CREATE TABLE profile_resource_grants (
  profile_id TEXT NOT NULL,
  resource_id TEXT NOT NULL,
  permissions INTEGER NOT NULL,
  granted_by_profile_id TEXT,
  grant_origin_json TEXT NOT NULL,
  created_at_ms INTEGER NOT NULL,
  PRIMARY KEY(profile_id, resource_id),
  FOREIGN KEY(profile_id) REFERENCES user_profiles(id) ON DELETE CASCADE,
  FOREIGN KEY(resource_id) REFERENCES connection_resources(id) ON DELETE CASCADE,
  FOREIGN KEY(granted_by_profile_id) REFERENCES user_profiles(id) ON DELETE SET NULL
);

CREATE TABLE profile_resource_settings (
  profile_id TEXT NOT NULL,
  resource_id TEXT NOT NULL,
  enabled INTEGER NOT NULL DEFAULT 1,
  settings_json TEXT NOT NULL,
  PRIMARY KEY(profile_id, resource_id),
  FOREIGN KEY(profile_id, resource_id)
    REFERENCES profile_resource_grants(profile_id, resource_id) ON DELETE CASCADE
);

CREATE TABLE profile_connection_bindings (
  profile_id TEXT NOT NULL,
  slot TEXT NOT NULL,
  resource_id TEXT NOT NULL,
  created_at_ms INTEGER NOT NULL,
  updated_at_ms INTEGER NOT NULL,
  PRIMARY KEY(profile_id, slot),
  FOREIGN KEY(profile_id, resource_id)
    REFERENCES profile_resource_grants(profile_id, resource_id) ON DELETE CASCADE
);

CREATE TABLE profile_migration_journal (
  migration_id TEXT PRIMARY KEY,
  stage TEXT NOT NULL,
  payload_json TEXT NOT NULL,
  updated_at_ms INTEGER NOT NULL
);

CREATE TABLE profile_data_generations (
  profile_id TEXT NOT NULL,
  generation INTEGER NOT NULL,
  state TEXT NOT NULL CHECK(state IN ('staging', 'visible', 'retired')),
  manifest_json TEXT NOT NULL,
  manifest_hash TEXT NOT NULL,
  created_at_ms INTEGER NOT NULL,
  updated_at_ms INTEGER NOT NULL,
  PRIMARY KEY(profile_id, generation),
  FOREIGN KEY(profile_id) REFERENCES user_profiles(id) ON DELETE CASCADE
);

CREATE UNIQUE INDEX one_visible_generation_per_profile
  ON profile_data_generations(profile_id)
  WHERE state = 'visible';

CREATE TABLE profile_restore_journal (
  restore_id TEXT PRIMARY KEY,
  mode TEXT NOT NULL CHECK(mode IN ('create', 'merge', 'registryReplace')),
  destination_profile_id TEXT,
  base_generation INTEGER,
  staged_generation INTEGER,
  stage TEXT NOT NULL,
  payload_json TEXT NOT NULL,
  updated_at_ms INTEGER NOT NULL,
  FOREIGN KEY(destination_profile_id) REFERENCES user_profiles(id) ON DELETE RESTRICT
);

CREATE TABLE job_ownership (
  backend TEXT NOT NULL,
  external_job_id TEXT NOT NULL,
  kind TEXT NOT NULL CHECK(kind IN ('download', 'recording', 'schedule', 'retry')),
  owner_profile_id TEXT,
  resource_id TEXT,
  profile_authorization_revision INTEGER NOT NULL,
  resource_authorization_revision INTEGER,
  created_at_ms INTEGER NOT NULL,
  terminal_at_ms INTEGER,
  detached_owner_token TEXT,
  PRIMARY KEY(backend, external_job_id),
  CHECK(owner_profile_id IS NOT NULL OR
    (terminal_at_ms IS NOT NULL AND detached_owner_token IS NOT NULL)),
  FOREIGN KEY(owner_profile_id) REFERENCES user_profiles(id) ON DELETE RESTRICT,
  FOREIGN KEY(resource_id) REFERENCES connection_resources(id) ON DELETE RESTRICT
);

CREATE TABLE owned_artifacts (
  id TEXT PRIMARY KEY,
  kind TEXT NOT NULL CHECK(kind IN ('download', 'recording')),
  owner_profile_id TEXT,
  canonical_path TEXT NOT NULL,
  ownership_state TEXT NOT NULL CHECK(ownership_state IN ('assigned', 'unassigned', 'detached')),
  detached_owner_token TEXT,
  size_bytes INTEGER,
  modified_at_ms INTEGER,
  created_at_ms INTEGER NOT NULL,
  UNIQUE(kind, canonical_path),
  CHECK((ownership_state = 'assigned' AND owner_profile_id IS NOT NULL) OR
    (ownership_state != 'assigned' AND owner_profile_id IS NULL)),
  FOREIGN KEY(owner_profile_id) REFERENCES user_profiles(id) ON DELETE RESTRICT
);
```

`profile_connection_bindings` makes singleton/default resource selection deterministic; a grant alone never implies a default. `visible_data_generation` selects immutable preference/DB/file paths such as `p.<profileId>.g.<generation>.<logicalKey>` and `profiles/<profileId>/g/<generation>/...`. A captured `ProfileScope` includes profile ID, visible data generation, and session epoch. The service transaction must ensure exactly one visible generation matches each active profile. Version and validate `policy_json`, `grant_origin_json`, resource settings, public configuration, generation manifests, migration/restore payloads, and sealed payload schemas; reject unknown future versions safely.

`granted_by_profile_id` is nullable audit attribution rather than operational ownership, so its deliberate `ON DELETE SET NULL` is paired with the immutable non-secret `grant_origin_json` snapshot. Operational profile/resource/job/artifact foreign keys remain restrictive or cascade only for true dependent configuration rows.

The restore coordinator also owns dedicated staging tables mirroring the resource/grant/settings/binding graph and keyed by `restore_id`, or a complete shadow registry database for comprehensive replacement. Staged rows are never queried by normal resource services. Publication copies/promotes them and changes the visible generation in the same authoritative SQLite transaction; cleanup may happen later.

Do not put download/recording execution payloads into this SQLite database merely for centralization. `job_ownership` is a reconciliation and authorization ledger, not an execution queue. Android native services and downloader plugins must work without a Flutter engine; their durable stores remain authoritative and gain owner/resource/profile-revision/resource-revision fields. Increment the profile authorization revision for role, feature-policy, or grant changes; increment the resource revision for credential rotation, disablement, ownership, or public configuration changes. PIN lock changes invalidate UI/remote session epochs but do not invalidate job authorization. `owned_artifacts` preserves ownership of completed files that are otherwise discovered by directory enumeration. Normalize canonical paths per platform before enforcing uniqueness. Unknown or detached artifacts are visible only in an Admin recovery view. Owner/resource foreign keys are restrictive: cancel, transfer, or detach terminal dependents in an explicit disposition transaction before profile/resource deletion. An incomplete disposition must make deletion fail at the database layer.

Connection secrets must never be plaintext in SQLite. Seal them with a versioned authenticated-encryption envelope whose associated data includes resource ID, resource type, owner profile ID, schema version, and payload version so ciphertext cannot be swapped between rows. Store/protect the device key through the platform `DeviceKeyProvider` contract below. A profile PIN never encrypts or unwraps resource secrets.

On tvOS, the authoritative secret is the runner-only Keychain shard referenced by the published recovery manifest; the purgeable SQLite row contains only a non-secret item reference and/or rebuildable sealed projection. The Top Shelf extension never receives that access group.

### Platform device-key contract

`DeviceKeyProvider` exposes non-exportable or wrapped versioned AEAD keys by key ID; resource code never reads raw platform credentials or derives a key from device identifiers. Key creation is device-bootstrap work, while legacy-secret conversion is profile migration work and must not occur during an unscoped warm-up.

| Platform | Required provider | Loss/availability behavior |
|---|---|---|
| Android / Android TV | Android Keystore hardware-backed AES wrapping key where available | Invalidation marks affected resources `reauthenticationRequired`; never replace the key and silently discard ciphertext |
| iOS / tvOS / macOS | Keychain item with documented accessibility and access group; no resource secret is exposed to the Top Shelf extension | Missing item enters resource recovery; tvOS recovery envelope keeps only Keychain references |
| Windows | DPAPI `CurrentUser` protected wrapping key with explicit application entropy/version | Different Windows user or unusable DPAPI state requires credential re-entry/import |
| Linux | Secret Service/libsecret item | If unavailable, require an Admin-created vault passphrase and store only an Argon2id-wrapped device key; do not silently fall back to device-ID obfuscation |

- Keep a key ID and envelope version with every sealed payload.
- Rotate by creating the next key, journaled rewrapping/re-encrypting every payload, verifying decryptability, then retiring the previous key. Crash recovery must accept both recorded generations until commit.
- Exclude wrapping keys and device-bound ciphertext from automatic OS backup/device transfer. v3 backup decrypts authorized resources and re-encrypts the portable package with its backup passphrase; restore seals them with the destination provider.
- On key loss, keep public resource metadata/grants but disable use and request re-entry or encrypted-backup restore. Never log decryption material or turn a decrypt failure into an empty credential write.
- Test key creation, use, rotation, concurrent access, invalidation/loss, app upgrade, OS backup exclusion, and platform fallback on real/supported targets.

Treat an entire configured URL as secret when it may embed tokens, usernames, or passwords. This includes Stremio manifests and many M3U/XMLTV URLs.

### Grant permissions

Use a bitmask or typed set with these initial permissions:

- `use`: browse/play/read through the connection.
- `download`: create local downloads.
- `writeRemote`: add torrents, mutate libraries, delete or rename remote items.
- `manage`: edit connection configuration and profile-local connection settings.
- `revealSecret`: display/copy the underlying credential or URL.
- `share`: grant the resource to another profile.

Admin role alone must not silently grant day-to-day access to every resource. Admins manage profiles, but resource ownership/grants remain explicit. A deliberate Admin recovery surface may enumerate all resources and transfer ownership after Admin re-authentication and confirmation; it must not silently change the active profile's normal grants.

### Profile feature policies

Start with stable feature bundles rather than individual preference locks:

```text
cloud
torrentSearch
addonsAndEngines
trackersAndDiscovery
iptv
debrifyTv
stremioTv
youtube
downloads
recordings
externalPlayers
incomingLinks
remoteControl
remoteTransfer
backupRestore
manageConnections
manageProfiles
appUpdates
allowAdultContent
```

Policies must be enforced in services/commands and route entry points, not only by hiding navigation items. Authorization is always the intersection of role ceiling, profile feature policy, resource grant permissions, resource state, and job capability. Imported or future policy fields cannot elevate a `member` or `child` into profile administration.

Use this first-release role ceiling:

| Capability | Admin | Member | Child |
|---|---|---|---|
| Create/edit/delete profiles, roles, policies, and cross-profile grants | Allowed when `manageProfiles` is enabled | Never | Never |
| Device reset, multi-profile backup/restore, app updates, resource recovery | Admin-only and requires re-authentication for sensitive actions | Never | Never |
| Own/manage a connection | Allowed when `manageConnections` is enabled | May own/manage its own resources when enabled; cannot grant them to another profile | Cannot own/manage/reveal/share resources in v1 |
| Use content/playback features | Subject to feature policy and grants | Subject to feature policy and grants | Subject to feature policy and grants; `allowAdultContent` is always false |
| Remote mutations/downloads | Subject to policy and resource permission | Subject to policy and resource permission | `writeRemote` is never effective; downloads/recordings require an explicit Admin-enabled policy and grant |
| Export one profile | Allowed | Allowed only when `backupRestore` is enabled and secrets require `revealSecret` | Admin-mediated only |

The registry must preserve at least one enabled Admin whose `manageProfiles` policy is effective. Updates to role, policy, PIN reset, disablement, and deletion must check this invariant in the same transaction.

## Task 12: Upgrade backup, restore, remote transfer, reset, and analytics

### One restore pipeline for every source

File restore and remote receive must never have separate write logic. Both feed a canonical `PortableProfilePackage` through this pipeline:

```text
decode/authenticate
  -> adapt source version
  -> enforce hostile-input limits and validate
  -> summarize
  -> select/authorize destination
  -> build explicit conflict plan
  -> build and verify an invisible shadow generation
  -> atomically publish visible generation
  -> recover/finalize journal
  -> resumable network-dependent follow-up
  -> detailed report
```

“Atomic” here means that readers resolve either the complete old generation or the complete new generation. It never claims one transaction spans SharedPreferences, independent SQLite databases, files, Keychain/Keystore, and native stores.

- [ ] Make `ProfileRestoreCoordinator` the only production API allowed to apply backup or remotely received configuration. Existing category handlers become decoders/adapters and cannot write `StorageService` directly.
- [ ] Require an explicit destination profile and captured authorization context before staging. A sole unpinned Admin may be preselected but is still shown in the confirmation summary; multi-profile installs never infer the destination from whichever profile is active when the last packet/file finishes.
- [ ] Let an Admin create a destination from the restore wizard. Keep that profile hidden/incomplete until restore commit, require the Admin to choose name/role/policy, never inherit a PIN, and delete the staged row on rollback. A legacy v1/v2 file has no profile identity, so it cannot choose these values itself.
- [ ] Snapshot the destination profile ID, session epoch, profile authorization revision, restore policy, and resource permissions at confirmation. Abort/reconfirm if role, policy, lock/session, grant, or destination state changes before commit.
- [ ] For create/merge restore, reserve `restoreId`, base visible generation, and a new data generation. Write all preferences to the new generation prefix; construct complete profile SQLite databases/files under an unpublished generation directory; put new/replacement resources, grants, settings, and bindings in SQLite staging tables keyed by `restoreId`; and record hashes/counts in `profile_data_generations.manifest_json`.
- [ ] Fsync/close where supported and verify every staged database, file hash, reference, role/grant invariant, resource envelope, and disk-space margin. No service may discover a generation by directory scanning; only the registry's visible-generation pointer grants visibility.
- [ ] Publish a single-profile restore in one `profiles.db` transaction that moves staged resource graph rows into live tables, changes a new profile's `lifecycle_state` from staging to active, changes `visible_data_generation`, retires the old generation, and marks the restore journal `published`. Do not change `active_profile_id` unless the user explicitly chose activation; if restoring the current profile, freeze actions and publish a new Flutter session/root immediately after commit while captured old operations remain bound to the retired generation. On tvOS, publish the equivalent complete recovery-store generation last and rebuild the projection from it.
- [ ] On startup, a journal before `published` leaves the old generation visible and cleans/retries staging; a journal at/after `published` uses the new generation and completes cleanup/follow-up. Never use inverse category writes as the primary crash-recovery mechanism.
- [ ] For comprehensive registry replacement on non-tvOS, construct and verify a shadow registry database plus every profile generation first. Under the single-instance/global maintenance lock, close the current registry and write/fsync `registry-swap-journal-v1.json` in durable support storage with old/staged/previous paths, hashes and stage; rename the current registry to a retained previous file; atomically rename the staged same-volume registry into place; reopen/verify; mark committed; then prune later. Bootstrap resolves a crash at every rename boundary from the journal/hashes and never guesses from modification time. tvOS instead publishes one complete `TvOsProfileRecoveryStore` generation and regenerates its projection.
- [ ] Run network-dependent addon/engine fetches and optional account validation after visibility publication as resumable follow-up work. Report partial network failures without rolling back already verified local categories or silently dropping them.
